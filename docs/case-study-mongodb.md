# MongoDB 조회 1.8s → 0.7s — $lookup 다이어트와 파이프라인 재배치

> ITIL 4 기반 통합 ITSM/ITAM 신제품 · 100만 건+ 컬렉션 · 2025~2026
>
> **게시 전 확인 체크리스트** — `[확인]` 표시 문단은 일반적인 패턴 기준으로 서술한 것이니,
> 실제 구현과 일치하는지 확인 후 게시하세요. 고객사명·실제 필드명은 이미 일반화되어 있습니다.

## 배경

담당하던 모듈에서 가장 트래픽이 많은 화면 두 곳 — **요청(티켓) 목록**과 **포털 통합검색** — 이 문제였다.
요청 컬렉션은 100만 건을 넘겼고, 목록 조회 응답이 평균 **1.8초**, 피크 시간대에는 **요청의 3%가 timeout**으로 떨어졌다.

이 제품은 Spring Cloud 기반 MSA 구조에 MongoDB를 주 저장소로 쓰고, 멀티테넌트를 지원한다.
요청 목록 한 화면에 요청 자체 정보 외에 **요청자·담당자·부서 이름, 소속 카탈로그/서비스, 상태·코드성 라벨**까지
함께 보여줘야 해서, aggregation 파이프라인에 `$lookup`이 겹겹이 쌓여 있었다.

## 진단 — explain부터

추측으로 인덱스를 늘리는 대신 `explain()`으로 파이프라인 실행 단계를 확인했다. 드러난 문제는 두 가지였다.

**1. `$match`가 파이프라인 뒤쪽에 있었다.**
필터 조건이 `$lookup` 이후에 적용되고 있어서, 화면에 20건을 보여주려고
조인 대상이 아닌 문서까지 전부 조인한 뒤 버리고 있었다. 100만 건 컬렉션에서 이 구조는 데이터가 늘수록 선형으로 느려진다.

**2. 없어도 되는 `$lookup`이 있었다.**
조인 대상을 뜯어 보니 성격이 달랐다.

| 조인 대상 | 성격 | 판단 |
|---|---|---|
| 사용자/부서 정보 | 변경 가능, 표시용 | 조인 유지가 맞음 — 단, 필터링 후로 |
| 카탈로그·서비스 연관 | 변경 가능, 업무 로직에 필요 | 유지 |
| 상태·코드성 데이터 | 사실상 정적 (코드 테이블) | **조인할 이유가 없음** |

## 개선

### 1. `$match`(와 `$sort`)를 파이프라인 맨 앞으로

필터·정렬을 `$lookup`보다 앞에 두면 두 가지가 한 번에 해결된다 —
**인덱스를 탈 수 있게 되고**, 조인은 화면에 나갈 문서(페이지 크기만큼)에만 수행된다.
개선의 체감 효과 대부분이 이 재배치에서 나왔다.

### 2. 코드성 데이터 `$lookup` 제거

상태명·코드 라벨처럼 사실상 정적인 데이터는 매 조회마다 DB에서 조인할 이유가 없다.
`[확인]` 애플리케이션 레벨에서 코드 매핑을 캐시해 두고 응답 조립 시 붙이는 방식으로 전환해,
파이프라인의 `$lookup` 수 자체를 줄였다.

### 3. 필터 패턴에 맞춘 복합 인덱스

`[확인]` 실제 화면의 필터 사용 패턴(상태·유형 등 equality 조건 + 생성일 정렬)을 기준으로
복합 인덱스를 재설계했다. 원칙은 equality 필드를 앞에, 정렬 필드를 그 뒤에 두는 것(ESR) —
인덱스가 정렬까지 흡수하면 메모리 소트가 사라진다.

### 4. 통합검색 — text index로, 인프라 추가 없이

요청·카탈로그·KEDB 등 6개 카테고리에 정보가 흩어져 있어 사용자가 어디서 검색해야 할지 몰랐고,
기존 LIKE(정규식) 검색은 느리고 부정확했다.

Elasticsearch 도입도 검토했지만 선택하지 않았다. 근거는:

- 구축형(온프레미스) 납품 제품이라 **고객사 인프라에 검색 엔진이 하나 더 늘어나는 것 자체가 운영 부담**
- 검색 요구 수준이 형태소 분석까지는 아니고, 필드 가중치 정도로 충분
- MongoDB text index는 이미 있는 인프라로 해결 가능

카테고리별 컬렉션에 text index를 구성하고, 각 컬렉션을 검색한 결과를 **한 화면에서 통합 제공**하는 방식으로 구현했다.

## 결과

| 지표 | Before | After | 근거 |
|---|---|---|---|
| 목록 조회 응답 | 1.8s | 0.7s (↓61%) | 동일 조건 API 응답 로그 비교 |
| timeout 비율 | 3% | 0% | API 응답 로그 |
| 검색 동선 | 화면별 개별 검색 | 한 화면 통합 검색 | — |

## 배운 것

- **인덱스를 늘리기 전에 파이프라인 순서부터.** 병목의 원인은 인덱스 부재가 아니라
  인덱스를 탈 수 없는 파이프라인 구조였다. explain 없이 인덱스만 추가했다면 쓰기 비용만 늘었을 것이다.
- **조인 대상의 '성격'을 나누면 지울 수 있는 게 보인다.** 변하는 데이터와 사실상 정적인 데이터를
  같은 방식($lookup)으로 다루고 있던 것이 낭비의 근원이었다.
- **인프라를 늘리지 않고 푸는 선택지를 먼저 검토한다.** 구축형 제품에서는 기능의 완성도만큼
  고객사 운영 복잡도가 중요하다. text index는 '충분히 좋은' 해법이었다.
